## The bug that doesn't look like a bug

Here's a situation worth sitting with for a second, because it's the reason this lesson exists.

You have an <Term>endpoint</Term> that calculates a price. Someone sends it a request. It replies
<Term of="200 ok">200 OK</Term> — the success code. No error in the logs. No alert. Nothing crashed.

And the price it returned is `null`.

Not "wrong by a bit". Not a crash you can go and look at. Just quietly, confidently wrong. The
endpoint did its job as far as it knows. Your editor showed no red squiggles when you wrote it, and
TypeScript compiled it without a word of complaint.

So what happened?

## The one idea

Think of a <Term of="type annotation">TypeScript type</Term> as a **label you write on a box**.

The labels are genuinely useful. While you're packing and moving boxes around, they tell you what's
supposed to be inside each one, and your editor uses them to stop you putting a lamp in the box
marked "books".

But here's the part that changes how you see everything else: **when your code actually runs, the
labels are gone.** TypeScript <Term of="compile">compiles</Term> down to plain JavaScript, and that
step peels every label off and throws them away. The boxes still move around. Nothing is checking
their contents anymore. (The formal name for this is
<Term of="type erasure">type erasure</Term>, and it is not a flaw — it is what keeps types free at
<Term>runtime</Term>.)

For boxes that never leave your house, that's fine — you packed them, you know what's in them.

The trouble starts with a box that arrives **from outside**: a <Term of="request body">request from
a browser</Term>, a webhook from another company, a <Term of="json">JSON</Term> file you saved last
month, a response from an API. You didn't pack that one. Writing a label on it doesn't change what's
inside. It just makes you, and everyone reading your code afterwards, *believe* something you never
actually checked.

## Why it usually doesn't crash

This is the part that catches people out, so it's worth being precise about.

You might reasonably think: fine, if the data is wrong, the code will explode and I'll see it in the
logs. Usually it won't. JavaScript is extremely reluctant to stop.

Multiply a number by something that isn't there and you don't get an error, you get
<Term of="nan">NaN</Term> — a special value meaning "not a number". Keep going and it spreads through
every calculation it touches. Then, when the result is turned into JSON to send back, `NaN` isn't a
thing JSON can express, so it silently becomes `null`.

At no point did anything go wrong loudly. That is a <Term of="silent failure">silent failure</Term>,
and it is why this class of bug can live in production for months: **there is nothing to notice.**

## The mental model

Picture a building with an access policy.

The **policy** is a document. It says who's allowed in the server room, and it's precise and
genuinely valuable. Everyone writing it takes it seriously. But it is a document. It cannot
physically stop anyone from walking through the door.

The **turnstile** is the thing at the entrance that actually reads your badge. It's the only part of
the building that can say "you're not on the list."

TypeScript is the policy. A check that runs when your code runs is the turnstile.

And now the bit worth remembering: **the policy is shredded at the door.** It governs the code you
*write*. The turnstile governs the data that *arrives*. If you never install a turnstile, the policy
is fiction — and a well-written fiction is more dangerous than an obvious one, because everyone
downstream trusts it completely.

The door itself has a name worth knowing: a <Term>trust boundary</Term>. It is any point where data
you control meets data you don't.

## Why not just...?

Every alternative here is reasonable-sounding. Working through why each one loses is, I think, the
fastest way to actually own this idea.

### ...trust it, since I wrote both sides?

You wrote the app that sends the request *and* the endpoint that receives it, so the shape is
guaranteed. Right?

It's guaranteed *today*. It stops being guaranteed the moment anything drifts: someone's phone is
running a three-month-old build of your app, a <Term>serializer</Term> starts sending a number as a
string, a retry replays an old payload. "Both sides" isn't one thing you control — it's two things
that happen to agree right now.

### ...just check a couple of fields with an `if`?

This is real validation, and honestly it's fine for one or two fields. It stops scaling for two
reasons.

First, it usually checks the wrong thing. `if (!body.tier)` asks *"is something there?"* — but the
bug you'll actually hit is someone sending `"delux"` instead of `"deluxe"`. Something *is* there. It
passes. It's just not one of the values you support.

Second, you now have two separate things describing one shape: the type you wrote down, and the
checks that run. Only one of them executes. Add a field to the type and the checks quietly stop
covering everything, and nothing tells you.

### ...just use `any` and stop worrying about it?

<Term of="any">`any`</Term> is TypeScript's "stop checking this" switch. It solves the friction
instantly, and that's the problem: it doesn't stay put. Anything touched by an `any` value also
stops being checked, and it spreads outward from there. You don't lose type safety at one line, you
lose it along a path.

### ...let it crash and fix it then?

That's a genuinely fine strategy — for bugs that crash. This one returns `200 OK`.

## What to do instead

Instead of *claiming* what the data is, **check it, and let the check hand you back the data**. If
the check passes, you have something you actually know the shape of. If it fails, you find out
immediately, at the door, where you can still do something about it.

That move has a name — <Term>parse</Term>, as opposed to merely asserting — and the description you
check against is called a <Term>schema</Term>.

The library below is Zod, but the idea has nothing to do with Zod specifically — you could write
this by hand. Don't worry about memorising the syntax; follow the shape of it.

```ts
import { z } from "zod";

const QuoteInput = z.object({
  customerId: z.string().min(1),
  squareFeet: z.number().int().positive(),
  tier: z.enum(["basic", "premium"]),
});
type QuoteInput = z.infer<typeof QuoteInput>;
const RATE: Record<QuoteInput["tier"], number> = { basic: 180, premium: 250 };

// The claim. `as` tells the compiler what to believe. It checks nothing.
export async function priceQuoteUnsafe(req: Request) {
  const input = (await req.json()) as QuoteInput; // still unchecked bytes
  // "1200" * undefined -> NaN, which JSON turns into null. Still a 200.
  return Response.json({ total: input.squareFeet * RATE[input.tier] });
}

// The check. safeParse looks at the real data and reports what it found.
export async function priceQuote(req: Request) {
  let body: unknown;
  try { body = await req.json(); } catch { body = null; }

  const parsed = QuoteInput.safeParse(body);
  if (!parsed.success) {
    return Response.json({ issues: parsed.error.issues }, { status: 400 });
  }
  const { squareFeet, tier } = parsed.data; // now genuinely known to be safe
  return Response.json({ total: squareFeet * RATE[tier] });
}
```

## Reading that, block by block

**The description at the top.** `QuoteInput` describes the shape once: an id that isn't empty, a
size that's a whole positive number, and a tier that must be one of exactly two words. Notice it's
written as a *value* — something that exists when the code runs and can actually inspect things —
rather than as a type annotation that evaporates.

**The line that says `type QuoteInput = z.infer<...>`.** This asks the description to also hand you
a TypeScript type. It matters because it means you only wrote the shape *once*. The thing that
checks and the thing that describes can't drift apart, because they're the same thing.

**The unsafe version.** One line does the damage: `as QuoteInput`. That's a
<Term of="type assertion">type assertion</Term> — you telling the compiler "trust me, it's this
shape". It generates no code whatsoever; at runtime that line may as well not exist. The compiler
now believes `squareFeet` is a number and is simply wrong. Send it a misspelled tier and you get the
silent `null` from earlier.

**The safe version, in three moves.** Read the body into a variable labelled
<Term of="unknown">`unknown`</Term>, which is TypeScript's way of saying "I genuinely don't know yet,
and I won't let you use this until you find out". Run the check. If it failed, stop right there and
reply <Term of="400">400</Term> — *your request was malformed* — along with the specific list of
what was wrong. Everything after that point is code that is finally allowed to trust its inputs.

The business logic at the bottom is identical in both versions. The only difference is whether the
assumptions it makes happen to be true.

## What the two paths actually look like

```
              data arrives from outside
                        |
          +-------------+-------------+
          |                           |
    "as QuoteInput"            check the data
    (a claim)                  (a question)
          |                           |
    nothing runs           +----------+----------+
          |                |                     |
          v            it's fine            it's not
   wrong data flows        |                     |
   onward as if fine       v                     v
          |          do the work          reply 400 and
          v                                say what's wrong
   200 OK, wrong answer
```

The thing to notice: the left path has **no fork in it**. There is nowhere in it where bad data
*could* be caught. That's not a missing check you forgot to add — the shape of the code makes
catching it impossible.

## Where this goes wrong in practice

**Writing a type on something you read from disk or the network.** `const settings: Settings =
JSON.parse(raw)` looks like it's checking something. It isn't. `JSON.parse` returns "could be
anything", and "could be anything" is allowed to become any type without complaint.

**Throwing on bad input.** Most check libraries offer a version that throws. In a request handler
that turns a caller's typo into a <Term of="500">500</Term> — a status that says *your server broke*
— when the honest answer was a 400. Reach for the version that returns a result you can branch on.

**Checking in the wrong place, over and over.** People often add checks deep inside, wherever the
last bug happened to surface. Then every new caller is a new hole. Check once, at the door where the
data enters, and let everything inside trust it. One turnstile at the entrance beats a guard in
every room.

**Assuming the failure will be loud.** Worth saying twice, because it's the whole point: a crash is
a *good* outcome. It tells you. The bug in this lesson doesn't crash — it answers confidently and
incorrectly, and that's much harder to find.

## Try this

You don't need a project for this. A scratch file is enough.

1. Write a function that takes something unknown and returns either `"basic"`, `"premium"`, or
   `null`. Start from `const TIERS = ["basic", "premium"] as const;` and use
   `TIERS.find(t => t === raw)`. Look at what you just did: you checked the real value, and got back
   either a known-good answer or an honest "no". That's a turnstile, in about six lines, with no
   library at all.
2. Now write the broken version: `const tier = raw as "basic" | "premium"`. Call both with the
   string `"delux"`, then with the number `7`.
3. Before you run it, predict what each one gives you. Then check. The interesting part isn't which
   one is wrong — it's that **neither of them produced a single compiler error.**

<Quiz>
  <Question q="Why can't a type annotation protect you from bad data arriving over the network?">
    Because the annotations are removed when TypeScript compiles to JavaScript. They shape the code you write, but by the time real data shows up there is nothing left to compare it against.
  </Question>
  <Question q="Why is a silent wrong answer worse than a crash?">
    A crash tells you. It has a time, a stack trace, and something to fix. A wrong answer returned with a success code looks exactly like a correct one, so nobody investigates — it can sit in production for months.
  </Question>
  <Question q="If you write both the app sending the data and the endpoint receiving it, why still check?">
    Because the two sides agreeing is a fact about right now, not a guarantee. Old app versions, changed serializers and replayed requests all break the agreement without anyone editing the endpoint.
  </Question>

<Takeaway>
A type is a promise **you** make to the compiler. A check is a promise the **data** makes to you.
Only one of them is still around when the code runs — so put a turnstile at every door where data
comes in, and let everything inside the building trust its badge.
</Takeaway>
