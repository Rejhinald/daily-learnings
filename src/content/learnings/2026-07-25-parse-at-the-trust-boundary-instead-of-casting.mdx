<InBrief principle="A type is a promise you make to the compiler. A check is a promise the data makes to you.">

TypeScript checks the code you *write*. Nothing checks the data that *arrives*. Every type is
deleted before your program runs, so labelling a request body does not inspect it — it just makes
everyone downstream believe you did.

When the data turns out to be a different shape, JavaScript usually will not crash. It produces
`NaN` or `undefined`, keeps going, and returns a confident, wrong answer with a success code.

The fix is to stop *claiming* and start *asking*. Run a real check on the data at the moment it
enters your program, and let that check hand you back the value. Then everything after it is
allowed to trust its inputs.

</InBrief>

## The quote that came back empty

It's a Tuesday. Someone in sales messages you: a customer generated a quote and the total showed up
blank. Not zero. Blank.

You open the logs, expecting red. There's nothing. No error, no stack trace, no alert. You find the
request. Status `200` — the code that means *everything went fine*. The response body is sitting
right there:

```json
{ "total": null }
```

So you read the handler. It's eleven lines. It takes the request, pulls out the square footage and
the tier, multiplies by a rate, sends the number back. You wrote it. It typechecks. Your editor is
completely calm about it — no red squiggles, no warnings, nothing to click.

And it is confidently returning nothing.

This is the moment worth slowing down for, because the instinct is to hunt for a typo, and there
isn't one. The code is doing exactly what it says. The problem is what it *assumed*.

## What was actually in the box

Here's the picture I keep coming back to.

A <Term of="type annotation">TypeScript type</Term> is a **label you write on a box**. It's genuinely
useful. While you're packing boxes and carrying them around your own house, the labels tell you and
everyone helping what's supposed to be inside. Your editor reads the labels and stops you putting a
lamp in the one marked *books*.

Then the code ships. And here's the part nobody tells you at the start: **when your program actually
runs, the labels are gone.**

TypeScript <Term of="compile">compiles</Term> to plain JavaScript, and that step peels every label
off and bins them. The boxes still move around. Nothing is reading them anymore. (The proper name for
this is <Term of="type erasure">type erasure</Term>, and it isn't a flaw — it's the deal that makes
types cost nothing at <Term>runtime</Term>.)

For boxes that never leave your house, fine. You packed them.

But that quote request didn't come from your house. It came over the network, from a browser you
don't control, possibly running a version of your app from three months ago. You didn't pack that
box. And writing *square footage: number* on the side of it changed nothing at all about what was
inside.

Somewhere out there, a client sent `squareFeet` as the text `"1200"` instead of the number `1200`.
The label still said number. Everyone believed it.

## Why nobody's pager went off

You'd expect that to explode. It's the reasonable expectation, and it's wrong, and understanding
*why* it's wrong is most of this lesson.

JavaScript is extraordinarily reluctant to stop. Ask it to multiply something by a value that isn't
there and it doesn't raise its hand. It hands you `NaN` — three letters meaning *not a number* —
and carries on as if nothing happened. `NaN` then spreads. Anything you multiply, add, or divide it
into becomes `NaN` too. It moves through the calculation like a rumour.

Then the result gets turned into <Term>JSON</Term> to send back. And JSON has no way to write `NaN`.
So it quietly becomes `null`.

Follow that chain again, because every link is boring on its own and the combination is what got
you: wrong type in → no error → `NaN` → serialised to `null` → sent with a `200`.

That's a <Term of="silent failure">silent failure</Term>. Not a crash you can find. An answer that
looks exactly like a correct answer. It can sit in production for months, and the only reason you
found this one is that a human happened to look at a blank field and say something.

## The building and the door

The mental model I'd like you to keep is a building with an access policy.

The **policy** is a document. It says who's allowed in the server room. It's precise, it's taken
seriously, everyone who writes it means it. But it is a document. It has never once physically
stopped anybody from walking through a door.

The **turnstile** is the thing at the entrance that reads your badge. It's the only part of the
building capable of saying *you are not on the list*.

TypeScript is the policy. A check that runs at runtime is the turnstile.

And the thing to hold onto: **the policy is shredded at the door.** It governs the code you *write*.
The turnstile governs the data that *arrives*. If you never install a turnstile, the policy is
fiction — and a well-written fiction is more dangerous than an obvious one, because everybody
downstream reads it and relaxes.

The door has a name, by the way. It's the <Term>trust boundary</Term>: any point where data you
control meets data you don't.

## The four things you'll want to try first

Every one of these is reasonable. I've reached for all of them. Here's where each one runs out.

**"I wrote both sides, so the shape is guaranteed."** It's guaranteed *today*. It stops being
guaranteed the moment anything drifts — a phone running an old build of your app, a
<Term>serializer</Term> that starts sending numbers as strings, a retry replaying a stale payload.
"Both sides" was never one thing you control. It's two things that currently agree.

**"I'll just check a couple of fields with an `if`."** Honestly fine for one or two fields. It fails
for a subtle reason: it usually checks the wrong thing. `if (!body.tier)` asks *is something there?*
The bug you'll actually hit is someone sending `"delux"` instead of `"deluxe"`. Something **is**
there. It sails through. It's just not a tier you sell.

**"I'll use `any` and stop fighting it."** That's the *stop checking this* switch, and it works
instantly, which is the trap. It doesn't stay where you put it. Everything an `any` value touches
also stops being checked, and it spreads outward from there. You don't lose safety on one line. You
lose it along a path, quietly.

**"If it's wrong it'll crash and I'll fix it then."** Genuinely a fine strategy — for bugs that
crash. Re-read the top of this lesson. This one returned `200`.

## Installing the turnstile

So: stop claiming, start asking. Describe the shape you need as something that *exists at runtime and
can actually look at a value*, then let it hand the value back to you.

That move is called <Term>parse</Term>, and the description you check against is a
<Term>schema</Term>. The library below is Zod. Don't worry about memorising it — you could write this
by hand. Follow the shape.

```ts
import { z } from "zod";

const QuoteInput = z.object({
  customerId: z.string().min(1),
  squareFeet: z.number().int().positive(),
  tier: z.enum(["basic", "premium"]),
});
type QuoteInput = z.infer<typeof QuoteInput>;
const RATE: Record<QuoteInput["tier"], number> = { basic: 180, premium: 250 };

// The claim. `as` tells the compiler what to believe. It checks nothing.
export async function priceQuoteUnsafe(req: Request) {
  const input = (await req.json()) as QuoteInput; // still unchecked bytes
  // "1200" * undefined -> NaN, which JSON turns into null. Still a 200.
  return Response.json({ total: input.squareFeet * RATE[input.tier] });
}

// The check. safeParse looks at the real data and reports what it found.
export async function priceQuote(req: Request) {
  let body: unknown;
  try { body = await req.json(); } catch { body = null; }

  const parsed = QuoteInput.safeParse(body);
  if (!parsed.success) {
    return Response.json({ issues: parsed.error.issues }, { status: 400 });
  }
  const { squareFeet, tier } = parsed.data; // now genuinely known to be safe
  return Response.json({ total: squareFeet * RATE[tier] });
}
```

## Walking through it

**The description, up top.** `QuoteInput` writes the shape down once — an id that isn't empty, a size
that's a whole positive number, a tier that's one of exactly two words. The important thing is that
it's a *value*, not an annotation. It exists when the program runs. It can be handed a thing and
asked about it.

**That odd double line.** `type QuoteInput = z.infer<typeof QuoteInput>` asks the description to
also produce a TypeScript type. It looks redundant and it's the opposite: it means the shape is
written down *once*. The thing that checks and the thing that describes can never drift apart,
because they're the same object.

**The unsafe version — one line of damage.** `as QuoteInput` is you leaning over to the compiler and
saying *trust me*. That's a <Term of="type assertion">type assertion</Term>. It emits no code at all;
at runtime the line may as well be a comment. From there the compiler is certain `squareFeet` is a
number, and it's wrong, and it will never find out.

**The safe version — three moves.** Read the body into a variable labelled
`unknown`, TypeScript's way of saying *I don't know what this is and I won't let you use it until
you find out*. Run the check. If it failed, stop right there and answer `400` — *your request was
malformed* — with the list of exactly what was wrong.

Notice what that early return buys you. Every line after it is code that has *earned* the right to
trust its inputs. The arithmetic at the bottom is identical in both versions. The only difference is
whether its assumptions happen to be true.

## The two paths, side by side

```
              data arrives from outside
                        |
          +-------------+-------------+
          |                           |
    "as QuoteInput"            check the data
    (a claim)                  (a question)
          |                           |
    nothing runs           +----------+----------+
          |                |                     |
          v            it's fine            it's not
   wrong data flows        |                     |
   onward as if fine       v                     v
          |          do the work          reply 400 and
          v                                say what's wrong
   200 OK, wrong answer
```

Look at the left path for a second. It has **no fork in it.** There's nowhere in it where bad data
*could* be spotted. That's not a check somebody forgot to write — the shape of the code makes
spotting it impossible. That's why the bug came out as a blank field instead of an exception.

## Where this bites in real life

**Putting a type on something you read from disk or the network.** `const settings: Settings =
JSON.parse(raw)` looks like it's checking. It isn't. `JSON.parse` returns *could be anything*, and
*could be anything* is allowed to become any type at all without a murmur.

**Checking in the wrong place, repeatedly.** People tend to add checks deep inside, wherever the last
bug surfaced. Then every new caller is a fresh hole. Check once, at the door. One turnstile at the
entrance beats a guard in every room, and it's less code.

**Using the throwing version inside a handler.** Most check libraries offer one that throws on bad
input. In a request handler that turns a caller's typo into a <Term of="500">500</Term> — a status
that means *my server is broken* — when the honest answer was a 400. Use the version that returns a
result you can branch on.

## Try this tonight

Ten minutes, a scratch file, no project needed.

Write a small function that takes something unknown and gives back `"basic"`, `"premium"`, or
`null`. Start from `const TIERS = ["basic", "premium"] as const;` and use
`TIERS.find(t => t === raw)`. Look at what you just built: it inspected the real value and returned
either a known-good answer or an honest *no*. That's a turnstile, in six lines, with no library.

Now write the broken twin: `const tier = raw as "basic" | "premium"`. Call both with the string
`"delux"`, then with the number `7`.

Before you run it, say out loud what each one will give you. Then run it. The interesting part isn't
which one is wrong — it's that **neither of them produced a single compiler error.** Both looked
equally fine while you were writing them. Only one of them was ever going to tell you the truth.

<Quiz>
  <Question q="Why can't a type annotation protect you from bad data arriving over the network?">
    Because annotations are deleted when TypeScript compiles to JavaScript. They shape the code you write, but by the time real data shows up there is nothing left to compare it against.
  </Question>
  <Question q="Why is a silent wrong answer worse than a crash?">
    A crash tells you. It has a time, a trail, and something to fix. A wrong answer sent with a success code looks exactly like a right one, so nobody investigates — it survives until a human happens to notice.
  </Question>
  <Question q="If you wrote both the app sending the data and the endpoint receiving it, why still check?">
    Because the two sides agreeing is a fact about right now, not a guarantee. Old app versions, changed serializers and replayed requests all break the agreement without anyone touching the endpoint.
  </Question>
</Quiz>

<Takeaway>
A type is a promise **you** make to the compiler. A check is a promise the **data** makes to you.
Only one of them is still standing when the code runs — so put a turnstile at every door where data
comes in, and let everything inside the building trust its badge.
</Takeaway>
